Project Structure ​

大部分代码都存放在 src 文件夹中, 例如:

md
src
|
+-- assets            # assets folder can contain all the static files such as images, fonts, etc.
|
+-- components        # shared components used across the entire application
|
+-- config            # all the global configuration, env variables etc. get exported from here and used in the app
|
+-- features          # feature based modules
|
+-- hooks             # shared hooks used across the entire application
|
+-- lib               # reusable libraries preconfigured for the application
|
+-- providers         # all of the application providers
|
+-- routes            # routes configuration
|
+-- stores            # global state stores
|
+-- test              # test utilities and mocks
|
+-- types             # shared types used across the application
|
+-- utils             # shared utility functions

为了便于扩展和维护, 需要将大部分代码组织在features文件夹中. 每个功能文件夹都应包含特定的功能代码, 这样能够使内容整齐地归类. 与平铺式的文件目录相比, 这种方法更且助于防止与功能相关的代码与共享组件混合, 从而使管理和维护代码库变得更简单. 通过采用这种方法, 你可以增强应用程序架构中的协作性/可读性和可扩展性.

目录结构 ​

一个功能目录的结构可能如下:

md
src/features/awesome-feature
|
+-- api         # exported API request declarations and api hooks related to a specific feature
|
+-- assets      # assets folder can contain all the static files for a specific feature
|
+-- components  # components scoped to a specific feature
|
+-- hooks       # hooks scoped to a specific feature
|
+-- routes      # route components for a specific feature pages
|
+-- stores      # state stores for a specific feature
|
+-- types       # typescript types for TS specific feature domain
|
+-- utils       # utility functions for a specific feature
|
+-- index.ts    # entry point for the feature, it should serve as the public API of the given feature and exports everything that should be used outside the feature

注意 ​

需要提供给其他模块使用的方法或组件, 都应该通过index.ts文件导入, 该文件将作为公共API的入口. 你应该仅使用如下方式导入其他组件或函数等.

ts
import { AwesomeComponent } from '@/features/awesome-feature'

而不是

ts
import { AwesomeComponent } from '@/features/awesome-feature/components/awesome-component'

Eslint配置规则 ​

限制import的目录 ​

这些规则, 我们可以通过Eslint配置规则并禁止这样的编码实现方式.

js
{
    rules: {
        'no-restricted-imports': [
            'error',
            {
                patterns: ['@/features/*/*'],
            },
        ],

    // ...rest of the configuration
}

防止循环依赖 ​

为了防止循环依赖, 可以使用另一个Eslint规则

js
{
    rules: {
        'import/no-cycle': 'error',
    // ...rest of the configuration
}

这么做, 主要是受NX如何处理独立但又需要供其他模块使用的库的启发, 将功能视为独立的库或模块, 但可以通过入口点, 将不同部分公开给其他模块使用. 这种方法还能够实现: 在将来更容易在单一存储库中拆分应用程序.

这样,你就可以确保代码库干净且易于维护.

如果你仍然遇到循环依赖关系, 你可以考虑将功能分解为更小的模块或将共享代码移至lib目录. 或者, 你也可以直接导入某个文件.

有时, 将整个API层移至 lib 目录可能会更有意义, 特别是需要在多个模块间共用的代码块.

Stores目录也是类似的道理, 若你有一个在整个应用中使用的全局存储器, 那么建议将它移至stores目录中.
